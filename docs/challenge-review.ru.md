**«Платежи фирм: создайте сервис пакетных платежей»**

Представьте, что вы backend-разработчик платформы управления бухгалтерской практикой, такой как TaxDome. На платформе работают тысячи фирм: от отдельных специалистов по подготовке налоговых деклараций до компаний с сотнями бухгалтеров. У каждой фирмы есть баланс на платформе, на который поступают платежи её клиентов по счетам.

Фирмы также сотрудничают друг с другом. Крупная компания передаёт часть деклараций независимым специалистам в разгар налогового сезона; бухгалтерская фирма поручает подготовку налоговых деклараций своих клиентов другому специалисту; компания, которая привела клиента, получает вознаграждение за рекомендацию.

Эти обязательства фирмы оплачивают средствами со своих балансов на платформе. Поэтому одна и та же фирма платит одним компаниям и получает деньги от других. Чтобы не оплачивать каждый долг отдельно, платформа позволяет сделать несколько платежей одним запросом.

**Ваша задача**

Написать веб-сервис, который принимает запрос на пакет платежей от одной фирмы и проверяет его допустимость: **денег на балансе плательщика должно хватать на все платежи в запросе.** Если денег недостаточно, весь запрос отклоняется.

- При отклонении вернуть HTTP **422**.
- В противном случае сохранить платежи в базе данных, списать деньги с баланса плательщика, зачислить их на балансы получателей и вернуть HTTP **201**.

Необходимо учитывать:

- Сервер работает в нескольких экземплярах за балансировщиком нагрузки.
- Предполагается использование PostgreSQL, MySQL или аналогичной реляционной базы данных.

**Инструменты**

Используйте один из языков: **Ruby, Python или Go**.

Разрешены любые AI-инструменты. Если вы ими пользуетесь, приложите **неотредактированные логи общения с LLM**. Не очищайте и не пересказывайте их: авторы хотят видеть исходную переписку.

По возможности предпочитайте распространённые библиотеки.

**Формат запроса**

Запрос представляет собой JSON-документ. Комментарии в документе приведены только для пояснения; в настоящих запросах комментариев нет.

| Поле | Значение |
|---|---|
| `payer_firm_uuid` | Публичный идентификатор фирмы, которая платит |
| `payments` | Массив платежей; каждый элемент — отдельный платёж одной фирме |
| `payments[].amount` | Сумма в долларах США **в виде строки**, с необязательной дробной частью до двух знаков. Всегда положительная |
| `payments[].payee_firm_uuid` | Публичный идентификатор получателя |
| `payments[].description` | Описание платежа |

В первом иллюстративном примере плательщик отправляет:

- `"1200.75"` фирме Lopez Bookkeeping — «Приведение бухгалтерии в порядок, 3 клиента».
- `"300"` фирме Nair Tax Services — «Вознаграждение за рекомендацию, 2 клиента».

**База данных платформы**

Есть две таблицы.

Таблица `firms`:

| Поле | Тип | Назначение |

Теперь — места, на которых я бы сосредоточил внимание.

**1. Несколько экземпляров сервера — самая сильная подсказка в задании.**

Допустим, у фирмы $100. Одновременно приходят два запроса на $80:

- Первый читает баланс $100 и считает, что денег достаточно.
- Второй тоже читает $100 и принимает такое же решение.
- Оба пытаются провести платежи.

Последовательное выполнение работает правильно, а параллельное может позволить потратить больше имеющегося баланса.

Блокировка внутри одного процесса приложения не координирует остальные экземпляры. Проверка средств и списание должны быть согласованы **на уровне общей базы данных**.

Причём просто завернуть обычное чтение и запись в транзакцию недостаточно: в PostgreSQL при стандартном `Read Committed` два обычных чтения могут увидеть один и тот же исходный баланс. Нужен корректный механизм блокировок или условного обновления. :chatgpt-content-reference{index="0"}

**2. Одна фирма может одновременно платить и получать деньги.**

Это отдельно подчёркнуто в описании бизнеса и, на мой взгляд, дано не случайно.

Нужно рассмотреть как минимум три ситуации:

- Несколько запросов списывают деньги с одного плательщика.
- Разные плательщики одновременно переводят деньги одному получателю.
- Фирма A платит B, пока B платит A.

Во втором случае легко потерять одно из зачислений, если оба запроса прочитают старый баланс получателя и затем запишут собственный результат.

В третьем можно получить взаимную блокировку: одна транзакция удерживает A и ждёт B, другая удерживает B и ждёт A. Для решения с блокировками строк разумный подход — блокировать **все затронутые фирмы в едином порядке**, например по `id`. Такой порядок рекомендует и документация PostgreSQL для предотвращения подобных deadlock. :chatgpt-content-reference{index="1"}

**3. Повторяющийся получатель в примере — явная проверка внимательности.**

Nair получает **два отдельных платежа**:

- $6,250.00;
- $5,800.50.

Отсюда следует:

- Повторение получателя допустимо.
- Нельзя складывать платежи в словарь так, чтобы второй заменил первый.
- В таблице `payments` должны сохраниться **три записи**, хотя получателей всего два.
- Для обновления баланса можно сложить суммы одного получателя, сохранив сами платежи отдельно.

Запрет повторяющихся получателей прямо противоречил бы их примеру.

**4. «Весь запрос отклоняется» означает отсутствие частичного результата.**

Недостаточно проверить, хватает ли денег на каждый платёж по отдельности.

При балансе $100 два платежа по $60 по отдельности допустимы, но пакет на $120 должен быть целиком отклонён.

Аналогично, если первый платёж уже записан, а на втором произошла ошибка, нельзя оставить:

- один проведённый платёж;
- частично изменённые балансы;
- списание без соответствующих зачислений.

Все записи платежей и изменения балансов должны составлять одну атомарную операцию. Ответ **201** следует отправлять после успешной фиксации этой операции.

**5. Формат денег описан довольно точно.**

Вход — строка в долларах. Хранение — целое число центов.

| Вход | Результат |
|---|---:|
| `"6250"` | 625000 центов |
| `"5800.5"` | 580050 центов |
| `"1200.75"` | 120075 центов |
| `"0.01"` | 1 цент |

Одного или двух знаков после точки требовать нельзя: в примере используются ноль, один и два знака.

Я бы разбирал строку непосредственно в целые центы либо использовал точный десятичный тип. Промежуточный `float` здесь создаёт ненужный риск ошибки.

Также нельзя молча округлить `"1.999"` до `"2.00"`: исходная сумма не соответствует указанному формату. Ноль и отрицательные суммы противоречат условию «всегда положительная».

**6. Денег должно быть достаточно ровно, без дополнительного запаса.**

Если баланс равен общей сумме платежей, запрос должен пройти, а баланс стать нулевым.

Проверка должна соответствовать условию:

`баланс >= сумма платежей`

Ошибка с `>` вместо `>=` — небольшой, но вполне вероятный предмет проверки.

**7. В `INTEGER` спрятан предел суммы.**

Если буквально выбрать PostgreSQL `INTEGER`, максимальное положительное значение — 2 147 483 647. В центах это **$21,474,836.47**. Выход за диапазон вызывает ошибку. :chatgpt-content-reference{index="2"}

При этом переполниться может не только отдельный платёж:

- сумма платежей;
- суммарное зачисление одному получателю;
- итоговый баланс получателя.

Это не повод автоматически менять схему. Нужно либо соблюдать указанные типы и обрабатывать границы, либо обоснованно выбрать `BIGINT` и явно отметить изменение в README.

**8. Повтор запроса и повтор получателя — разные вещи.**

В задании нет идентификатора пакета или ключа идемпотентности.

Представим: база успешно сохранила платежи, но клиент не получил ответ из-за обрыва соединения. Он повторяет запрос — деньги могут уйти второй раз.

При этом два полностью одинаковых запроса могут означать и два намеренных платежа. Поэтому автоматически считать одинаковые JSON дубликатами нельзя.

**Идемпотентность явно не требуется**, но её отсутствие и последствия стоит описать. Это хорошее улучшение для реального сервиса; вводить его как обязательное условие задания было бы нашим собственным расширением требований.

**9. «От одной фирмы» означает одного плательщика в запросе.**

По контексту это не сервис, навсегда привязанный к одной конкретной фирме. На платформе тысячи компаний, и каждая может быть плательщиком.

Следовательно, нельзя зашить Pinecrest или её UUID в логику. Три указанные фирмы — исходные данные для примера.

Также `uuid` из API и внутренний `id` в связях таблиц — разные идентификаторы. Их нужно корректно сопоставлять.

Есть и вопросы, на которые документ **не даёт однозначного ответа**. Здесь важно показать осознанное решение, а не выдавать догадку за требование.

| Неопределённость | Как я бы с ней поступил |
|---|---|
| Пустой массив `payments` | Выбрал бы отклонение и записал это как допущение |
| Неизвестный плательщик или получатель | Отклонял бы весь пакет без изменения данных; формат ошибки описал бы |
| Платёж самому себе | Явно определил бы правило: прямого запрета в тексте нет |
| Обязательность и допустимая пустота `description` | Зафиксировал бы правила валидации |
| Максимальное количество платежей и длина описания | Ввёл бы обоснованные ограничения либо отметил отсутствие лимитов |
| URL endpoint и тело ответа | Выбрал бы и задокументировал |
| Аутентификация и право списывать деньги конкретной фирмы | Описал бы границу ответственности сервиса; одного знания UUID для реального доступа недостаточно |
| Можно ли изменять предложенную схему | Все изменения перечислил бы явно |

Особенно интересен **платёж самому себе**. Если его разрешить, итоговый баланс от него не изменится. Но буквальное условие всё равно требует средств **на сумму всех платежей**.

Например: баланс $100, платёж себе $100 и другой фирме $100. Чистый отток составляет $100, а сумма пакета — $200. Проверять только чистый отток означало бы изменить заданное правило.

С HTTP-кодами тоже нужна аккуратность: **422 явно предписан для недостатка средств**. Из этого не следует, что любой сбой базы, повреждённый JSON или внутренняя ошибка должны превращаться в 422. Остальные ответы нужно определить отдельно.

В тексте я не обнаружил противоречий, которые делали бы основную задачу невыполнимой.

Проверка контрольного примера:

`6250 + 5800.50 + 1200.75 = 13251.25`

Все конечные балансы правильные. Общая сумма денег до и после — **$52,500.00**.

Первый JSON на странице 3 и контрольный запрос на странице 4 содержат разные платежи. Это **два разных примера**, поэтому расхождение сумм между ними нормально.

Есть небольшая техническая странность: в метаданных PDF указан заголовок `Redmine API authentication`. Он не соответствует содержимому и выглядит как след экспорта документа; дополнительных требований из этого не следует.

Отдельная важная часть проверки — **как мы работаем**. История коммитов, исходная AI-переписка, принятые допущения и ответы про время и удовлетворённость результатом входят в состав сдачи. Этот разбор уже относится к работе с AI по заданию, поэтому исходную переписку понадобится сохранить. Пересказ вместо неё прямо не соответствует инструкции.

Для будущей реализации я бы заранее определил следующие проверки — они покажут существенно больше, чем один успешный запрос:

| Проверка | Ожидаемый результат |
|---|---|
| Контрольный пример | 201, три записи платежей, точные балансы |
| Баланс точно равен сумме | Успех, остаток ноль |
| Каждый платёж помещается в баланс, весь пакет — нет | 422, никаких изменений |
| Два конкурентных списания по $80 при балансе $100 | Один успех, один отказ; остаток $20 |
| Разные плательщики одновременно платят одному получателю | Все зачисления сохранены |
| A платит B одновременно с B → A | Корректное завершение без частичных переводов |
| Ошибка после начала изменений | Полный откат |
| Повторяющийся получатель | Все платежи сохранены отдельными записями |
| Неверный формат суммы или выход за диапазон | Предсказуемый отказ без изменения балансов |

Конкурентные сценарии стоит проверять на выбранной реляционной базе с отдельными соединениями: последовательные вызовы или замоканная база такие ошибки могут просто не показать.
