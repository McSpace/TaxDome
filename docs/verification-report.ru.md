В полном наборе действительно выполняются HTTP-запросы через Nginx и напрямую к трём API с реальной PostgreSQL. Конкурентные тесты проверяют конкурирующие списания, общий счёт получателя, встречные переводы, цикл из трёх фирм, 200 одновременных запросов и видимость данных. Тесты отказов инъецируют ошибки после изменения балансов и после вставок, прерывают подключение к БД и проверяют таймауты. Это содержательные проверки, а не только проверки HTTP-статусов.

### Дополнительные независимые проверки

Написан отдельный проверочный сценарий, без импорта тестовых помощников репозитория. Состояние проверялось непосредственно в БД до и после HTTP-запросов.

1. Пакет из двух платежей по $20000 при балансе $36748.75, с разными описаниями: 422; оба платежа отсутствуют, все балансы прежние.
2. Корректный первый платёж и неизвестный второй получатель: 422; первый платёж также не применяется.
3. Сумма `1.001`: 422; изменений нет.
4. Три параллельных платежа по $80 при балансе $100: один 201, два 422; остаток $20. Перед освобождением блокировки подтверждено, что все три запроса одновременно ожидали блокировок PostgreSQL.
5. Через публичный Nginx реально достигнуты все три экземпляра: `api-1`, `api-2`, `api-3`.
6. Отдельно воспроизведены объявленные последствия ON: два одинаковых платежа по $20000 при балансе $36748.75 дают 201 и одну вставку; последующий платёж с теми же получателем/описанием, но другой суммой даёт 409 без изменений.

Результаты со снимками состояния: [independent-checks.json](verification-evidence/independent-checks.json).

## Замечания, требующие действий

### 1. Неполный комплект AI-логов

PDF, страницы 2 и 5, требует необработанные диалоги при использовании AI. [evidence/README.md, строка 6](https://github.com/McSpace/TaxDome/blob/620bf5993e179f9f24733f25f918cff7a7ba9e9f/evidence/README.md#L6) явно помечает транскрипт Claude Code как Pending. Файлы ранних разговоров есть, но документация прямо указывает, что это доступные снимки, а не гарантированно полные экспорты. Это формальный пробел сдачи, не assumption о продукте. Нужно приложить исходный экспорт сессии реализации и необходимые исходные диалоги.

### 2. Не заполнены два обязательных ответа

[README, строки 343–344](https://github.com/McSpace/TaxDome/blob/620bf5993e179f9f24733f25f918cff7a7ba9e9f/README.md#L343) содержат Pending вместо времени работы и самооценки. Их должен заполнить автор; придумывать ответы за него нельзя.

### 3. Первоначальный сбой сборки Docker

Первый `scripts/up.sh` завершился с `failed to solve: image "docker.io/library/taxdome-app:local": already exists`. Несколько сервисов в Compose объявляют один общий image и один build, и BuildKit пытался экспортировать его из нескольких целей. Причина выглядит как конфликт параллельного экспорта на данной версии Docker/Compose; универсальная воспроизводимость не установлена.

Обход без изменения исходников:

```sh
docker compose build api-1
docker compose up -d --no-build --wait
```

После этого обычный `scripts/up.sh` также прошёл. Полный тестовый скрипт успешно собирал окружения. Следовательно, это наблюдавшаяся проблема первого запуска, а не постоянная невозможность запуска или платёжный дефект. Для более надёжной сдачи полезно собирать общий runtime-образ один раз и документировать поддержанную среду.

## Объявленные assumptions и расширения

По условию проверки перечисленное ниже не записано в скрытые несоответствия.

**Дедупликация ON — наиболее существенное отличие.** PDF говорит о каждом элементе как об одном платеже и требует средств на все платежи запроса. Он не определяет идемпотентность и не задаёт уникальность описаний. Реализация по умолчанию отождествляет платежи по плательщику, получателю и точному описанию: одинаковая сумма пропускается, другая даёт 409. Поэтому она может вернуть 201 для пакета, полная сумма которого превышает баланс, и не вставить все его элементы. Это честно описано в README, включая ограничения, и воспроизведено независимо. В режиме OFF соответствие буквальной модели PDF ближе: каждый элемент записывается, средства нужны на весь пакет. Если проверяющий не согласовал ON как допустимый assumption, само объявление не превращает это изменение требований в формальное соответствие.

**Ограничения входа** — 1000 платежей, 1024 символа описания, 1 MiB тела и 32 символа суммы — отсутствуют в PDF, но явно документированы в README. Их следует считать заявленными ограничениями решения. Ограничение INTEGER для денег вытекает из предложенной схемы.

**Самоплатежи, пустые описания, регистр UUID, seed только в пустую таблицу, отсутствие управления фирмами и авторизации** — заявленные решения для открытых вопросов. Сам PDF не требует управления фирмами или авторизации, поэтому их отсутствие не является самостоятельным нарушением задания.

**Дополнительные статусы** 400/413/415/409/503 и т. п. описаны. Недостаток средств действительно возвращает требуемый 422. В PDF нет исчерпывающего контракта для невалидного JSON и инфраструктурных отказов; такие ответы не следует автоматически считать ошибками. 409 связан именно с дополнительной моделью ON.
