# Bulk Firm Payments Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the TaxDome bulk payment service exactly as specified in the PRD. It runs as three FastAPI instances behind Nginx, with PostgreSQL 18 as the single source of truth and an independent Pytest runner that proves the 151-case catalogue in both idempotency modes.

**Architecture:** The API strictly parses and validates the raw request bytes and converts amounts to integer cents. It then opens one `READ COMMITTED` transaction and calls a single `SECURITY DEFINER` PL/pgSQL function, `app.process_payment_batch(text, jsonb)`. That function locks every participant row in ascending `firms.id` order, classifies duplicates using the function-local mode setting, checks funds, inserts rows and applies per-firm deltas. The API commits and only then returns 201. A one-shot `db-init` service installs the schema, roles, function, mode and seed idempotently before the APIs start.

**Tech Stack:** Python 3.14 (`python:3.14-slim`), FastAPI 0.162, Pydantic 2.14, psycopg 3.3 (binary) + psycopg-pool 3.3, uvicorn 0.54, PostgreSQL 18 (`postgres:18`), Nginx 1.29 (`nginx:1.29-alpine`), Pytest 9.2, HTTPX 0.28, uv for locking, Docker Compose v2 profiles.

**Spec:** `docs/PRD.md` is the contract. Also read `docs/architecture.md`, `docs/database-algorithm.md` and the case inputs in `docs/Firm_Payments_Test_Scenarios.md`.

## Global Constraints

- All code, comments, docs and commit messages are in English.
- Tables stay exactly `firms(id INTEGER, name TEXT, balance_cents INTEGER, uuid TEXT)` and `payments(id INTEGER, payer_firm_id INTEGER, payee_firm_id INTEGER, amount_cents INTEGER, description TEXT)`. Do not add columns or application tables. Constraints and indexes are allowed, but there must be no unique constraint on the payment key.
- No ORM. Write SQL and PL/pgSQL directly. Never use floating point for money.
- Monetary ranges: balances `0..2147483647`, payments `1..2147483647`. Sums use `bigint`/`numeric` before the range check.
- Limits: batch size 1–1000; body ≤ 1048576 bytes; description 0–1024 code points with no U+0000; amount string ≤ 32 chars, matching `[0-9]+(?:\.[0-9]{1,2})?`; UUID in hyphenated 8-4-4-4-12 hex form, any case, lowercased for lookup.
- Mode input is `PAYMENT_IDEMPOTENCY_MODE`. It accepts exactly `on`/`off` and defaults to `on` only when unset. The authority is the function-local setting `app.payment_idempotency`. APIs never branch on an environment mode.
- Timeouts (env, defaults): `DB_POOL_TIMEOUT_SECONDS=5`, `DB_LOCK_TIMEOUT_MS=5000`, `DB_STATEMENT_TIMEOUT_MS=15000`. Nginx `proxy_read_timeout 30s`. Do not add automatic retries anywhere, and set `proxy_next_upstream off`.
- Only Nginx publishes a host port (`8080`). APIs and Postgres have no host ports.
- Do not add excluded features (PRD §2): auth, request keys, mode switching API, firm CRUD, queues, caches, metrics.
- Commit after each task. Commit messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Decisions this plan fixes (not stated in the PRD)

| --- | --- |
| DB layout | Database `taxdome`, schema `app` owned by NOLOGIN role `payments_owner`. Tables `app.firms` and `app.payments`. `payments.id` is `INTEGER GENERATED BY DEFAULT AS IDENTITY`. |
| Roles | `payments_owner` (NOLOGIN, owns everything). `payments_api` (LOGIN, password from `API_DB_PASSWORD`; only `USAGE` on `app` + `EXECUTE` on the batch function). The runner uses the `postgres` superuser, whose credentials are never given to APIs. |
| Function I/O | `app.process_payment_batch(payer_uuid text, entries jsonb) RETURNS jsonb`. Each entry is `{"payee_firm_uuid": text, "amount_cents": int, "description": text}`. The result is `{"inserted_count","skipped_count","gross_outgoing_cents","idempotency_mode"}`. |
| Function errors | Custom SQLSTATEs: `TD001` unknown_firm, `TD002` insufficient_funds, `TD003` numeric_overflow, `TD004` payment_amount_conflict, `TD005` invalid batch → validation_error, `TD006` invalid/missing mode → 503 temporarily_unavailable. `DETAIL` carries a JSON array for `details`. |
| Test hook | `app.test_hook(stage text, payer_id integer)` is a no-op owned by `payments_owner` with no PUBLIC execute. The function calls it at stages `after_validation`, `after_locks`, `after_history`, `after_payer_balance`, `after_payee_balance`, `after_payment_insert`, `before_return`. Only the runner replaces it inside the disposable test DB, to raise, block on an advisory lock or sleep. The production body does nothing. |
| Init | `app/migrate.py` (run by the `db-init` one-shot service from the app image) runs as superuser in one transaction under `pg_advisory_xact_lock`. It validates the mode, creates roles if missing, applies `db/*.sql` (all `IF NOT EXISTS` / `CREATE OR REPLACE`) and refuses to continue if an existing function's mode differs. It then sets the mode with `ALTER FUNCTION ... SET app.payment_idempotency` and seeds only when `app.firms` is empty. |
| Strict parsing | Parse raw bytes manually (no FastAPI body model). `json.loads` uses `object_pairs_hook` to reject duplicates and `parse_constant` to reject NaN/Infinity. A Pydantic v2 model with `strict=True, extra="forbid"` validates the shape. OpenAPI gets the model schema through `openapi_extra`. |
| Transaction | Pool connections use `autocommit=True`. Each batch runs `BEGIN ISOLATION LEVEL READ COMMITTED` → `SET LOCAL lock_timeout`/`statement_timeout` → `SELECT app.process_payment_batch(...)` → `COMMIT`. Any failure before `COMMIT` → `ROLLBACK` (or discard the broken connection). A failure during `COMMIT` → `commit_outcome_unknown`. |
| Test stacks | The project name is `taxdome-test-on`/`taxdome-test-off`. `compose.test.yaml` removes the Nginx host port, enables the `test-runner` service and shortens timeouts (pool 2 s, lock 2000 ms, statement 4000 ms). |
| Case IDs | Each test carries `@pytest.mark.case("BAS001", ...)`. The conftest writes the IDs and the mode into JUnit properties. `tests/unit/test_catalogue_coverage.py` fails if any `### XXX000` ID in the catalogue has no marker in `tests/`. |

## Review Focus

1. Description with a lone surrogate escape such as `"\ud800"` must return 422 `validation_error`, not a 500 from UTF-8 encoding in psycopg.
2. Integer literals with thousands of digits (Python raises `ValueError` past `sys.int_info.default_max_str_digits`) and very deeply nested arrays (`RecursionError`) must return 400 `invalid_json`, not 500.
3. A request without `Content-Length` (chunked) sent directly to an API with more than 1 MiB must get 413. The size limit is enforced while streaming, not by trusting the header.
4. A payer UUID in upper case and a payee UUID in lower case for the same firm is a self-payment. Normalization happens before the function resolves keys, so one row is locked and the net delta is zero.
5. 200 simultaneous requests (CON004) against a pool of `DB_POOL_MAX=10` per instance must queue and finish, not fail with 503, as long as they fit in the pool timeout. The test asserts there is no 5xx.

Function body order (PRD §7). Follow it exactly and call the hook at each named stage:
1. Read `current_setting('app.payment_idempotency', true)`; anything other than `on`/`off` → `TD006`. Validate `entries`: an array of 1..1000 objects with exactly these three keys, an integral `amount_cents` in 1..2147483647, a string description ≤ 1024 chars, and lowercase hyphenated UUIDs (`TD005`). Resolve the payer and payees; collect every unknown index → `TD001`. Hook `after_validation`.
2. `FOR fid IN SELECT DISTINCT unnest(participants) ORDER BY 1 LOOP PERFORM 1 FROM app.firms WHERE id = fid FOR UPDATE; END LOOP;` Hook `after_locks`.
3. In a separate statement, read the locked balances and the history: `SELECT payee_firm_id, description, array_agg(DISTINCT amount_cents) FROM app.payments WHERE payer_firm_id = $payer AND (payee_firm_id, description COLLATE "C") IN (batch keys) GROUP BY 1,2`. Hook `after_history`.
4. ON mode: for each entry in input order, a historical amount different from the entry amount (or more than one distinct historical amount) is a conflict. Equal → skip. An earlier in-batch occurrence with a different amount is a conflict; with the same amount → skip. Any conflict → `TD004` with every conflicting index. OFF mode: keep every entry.
5. Gross as `bigint`. If gross > payer balance → `TD002`. If gross = 0 → return the counts with no writes.
6. Compute per-firm net deltas and final balances in `bigint`. If any final balance falls outside `0..2147483647` → `TD003`.
7. Update the payer balance (hook `after_payer_balance`). Update each other firm in ascending ID order (hook `after_payee_balance` after each). Insert the kept rows in input order (hook `after_payment_insert` after each). Hook `before_return`. Return the jsonb.

Function attributes: `LANGUAGE plpgsql VOLATILE PARALLEL UNSAFE SECURITY DEFINER SET search_path = pg_catalog, pg_temp`. Schema-qualify every object. `03_privileges.sql`: `REVOKE ALL ON SCHEMA app FROM PUBLIC`; `GRANT USAGE ON SCHEMA app TO payments_api`; `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC`; `GRANT EXECUTE ON FUNCTION app.process_payment_batch(text,jsonb) TO payments_api`. Indexes: unique on `firms.uuid` and `payments_key_idx ON app.payments (payer_firm_id, payee_firm_id, (description COLLATE "C"))`. Checks: `balance_cents >= 0`, `amount_cents > 0`, `uuid ~ '^[0-9a-f]{8}-([0-9a-f]{4}-){3}[0-9a-f]{12}$'`. FKs from payments to firms.
